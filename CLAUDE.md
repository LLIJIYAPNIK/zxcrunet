# zxcrunet

Платформа для сайтов-визиток. Пользователь собирает визитку из готовых блоков и публикует её:
- **бесплатно на поддомене сервиса**: `имя.zxc.ru.net`;
- **на своём домене**: подтверждает владение TXT-записью и направляет A-запись на IP сервера.

Визитки бывают двух типов:
- **бизнес**: опыт, проекты, стек, контакты, резюме. Это профессиональная визитка;
- **личное**: игры, книги, аниме, сериалы, фильмы, посты, плейлист. Это блог о себе.

Админок две: **кабинет пользователя** (конструктор) и **админка владельца продукта**.

## Бренд

- Название и лейбл: **zxcrunet**, всегда строчными. Используется в логотипе, шапке, `<title>`, favicon, письмах и в плашке «Сделано на zxcrunet» в подвале каждой опубликованной визитки (ссылка на `https://zxc.ru.net`).
- Домен сервиса: `zxc.ru.net`.
- В макетах встречаются `NEON·ID`, `neon.id` и `имя.neon.id`. В коде их **всегда** заменяем на `zxcrunet`, `zxc.ru.net` и `имя.zxc.ru.net`.

## Дизайн

- Эталон: `design/Неоновые визитки — редизайн.html`. Оттуда берутся токены, неоновая палитра (пользователь выбирает один акцентный цвет, остальные выводятся из него), шрифты (Onest для текста и заголовков, JetBrains Mono для адресов, номеров и таймкодов), компоненты и состав блоков.
- `design/Неоновые визитки.html` лежит как архив. Используем его, только если в эталоне чего-то нет.
- Макеты весят по несколько мегабайт, внутри base64-картинки. Читаем их выборочно, через grep и вырезанные фрагменты, а не целиком.
- Mobile-first: кабинет должен быть удобен на телефоне, в эталоне есть экран «Админка на телефоне».
- Для фронтенд-задач есть скилл `.agents/skills/design-taste-frontend`.

## Структура монорепо

```
backend/            FastAPI-приложение (свой pyproject.toml, uv)
  src/zxcrunet/
    <context>/      bounded context: identity, sites, domains, catalog, moderation, analytics, plans
      domain/       сущности, value objects, доменные события, интерфейсы репозиториев. Без импортов фреймворков
      application/  use cases (команды и запросы), DTO, порты
      infrastructure/  SQLAlchemy-модели и репозитории, внешние клиенты
      api/          FastAPI-роутеры и схемы запросов/ответов
    shared/         общий код: UoW, базовые классы, конфиг, ошибки
    main.py
  migrations/       Alembic
  tests/            unit/ (домен и use cases без БД), integration/ (с реальным Postgres)
frontend/           Next.js
  src/app/
    (marketing)/    лендинг zxc.ru.net
    app/            кабинет пользователя (/app)
    admin/          админка владельца (/admin)
    _sites/[host]/  рендер опубликованных визиток (сюда переписывает middleware)
  src/blocks/       компоненты блоков: render + editor + схема настроек
infra/              docker-compose*.yml, Caddyfile, скрипты бэкапа
design/             HTML-макеты (эталон и архив)
```

Корневой `pyproject.toml` на этапе 0 переносим в `backend/`.

## Архитектура и правила кода

- **Clean Architecture и DDD.** Зависимости идут только внутрь: `api → application → domain`, `infrastructure` реализует порты домена и приложения. Домен не знает про FastAPI, SQLAlchemy и Pydantic.
- Bounded contexts не лезут в таблицы и модели друг друга. Общаются через application-сервисы или доменные события.
- Одна транзакция на use case, через Unit of Work.
- Код, идентификаторы и docstring пишем на английском. Тексты интерфейса и писем на русском, всегда через словари (`frontend/src/i18n/ru.ts`, на бэкенде коды ошибок плюс словарь), чтобы потом добавить EN.
- Ошибки API в едином формате `{"error": {"code": "...", "message": "...", "details": {...}}}`.
- Время хранится в UTC (`timestamptz`), ID — UUIDv7.
- Каждый новый use case покрываем unit-тестом, каждый эндпоинт интеграционным тестом. Задача готова, только если зелёные `ruff`, `mypy --strict`, `pytest`, `eslint`, `tsc`, `vitest`.
- Миграции Alembic только через autogenerate с ручной проверкой. Уже применённые миграции не редактируем.

## Доменная модель (основное)

- **User**: email, хэш пароля (argon2id), `email_verified_at`, роль (`user` | `owner`), статус (`active` | `blocked`), план.
- **Plan**: лимиты `max_sites`, `max_custom_domains`, `max_upload_mb`. Пока есть только `free` (3 сайта, 3 своих домена). Оплаты нет, но лимиты проверяются только через Plan, не константами в коде.
- **Site**: владелец, тип (`business` | `personal`), `slug` (поддомен), тема (акцентный цвет), статус (`draft` | `published` | `suspended`), SEO-поля. Сайтов у пользователя несколько, до лимита плана.
- **Page и Block**: у сайта есть страницы, у страницы упорядоченные блоки. Блок хранит `type`, `version` и `settings` (JSONB, валидируется Pydantic-схемой своего типа). Черновик и опубликованная версия хранятся раздельно: «Опубликовать» делает снимок черновика.
- **Slug**: `[a-z0-9-]`, 3–32 символа, без дефиса в начале и конце. Зарезервированные имена (`www`, `api`, `app`, `admin`, `mail`, `static`, `media`, `zxc`, `support`, `status` и т.п.) лежат в таблице, владелец правит её в админке.
- **CustomDomain**: сайт, хост, `verification_token`, статус (`pending` → `verified` → `active` | `failed` | `lost`), время последней проверки и ошибка.
- **Catalog**: `Title` — тип (`game` | `book` | `anime` | `series` | `film`), название, год, обложка, связь «серия/часть». `ShelfEntry` — статус (хочу / в процессе / готово / брошено), оценка, оценки по критериям, часы или прогресс, заметки, спойлерный текст. В MVP тайтлы вводятся вручную, у `Title` есть поля `source` и `external_id` под будущий импорт из API.
- **Post**: рецензия или заметка, может ссылаться на тайтл.
- **Report** (жалоба), **AuditLog** (действия владельца и модераторов), **PageView** (агрегаты по дням).

## Маршрутизация по хосту

- `zxc.ru.net`: лендинг, `/app` (кабинет), `/admin` (только роль `owner`), `/api/*` (Caddy проксирует в FastAPI).
- `*.zxc.ru.net` и активные пользовательские домены: Next.js middleware по заголовку `Host` переписывает запрос на `/_sites/[host]/...`. Сайт ищется через API `GET /api/public/sites/resolve?host=` с кэшем в Redis.
- Неизвестный хост → страница 404 zxcrunet. Сайт со статусом `suspended` → заглушка «Сайт недоступен».

## Свои домены

1. Пользователь вводит домен. Сервис выдаёт `verification_token` и инструкцию: TXT `_zxc-verify.<домен>` = токен и A `<домен>` → IP сервера (для `www` — CNAME на `<домен>`).
2. Фоновая задача проверяет записи: сразу, потом с backoff в течение 48 часов. Проверку можно запустить вручную кнопкой.
3. Когда обе записи совпали, статус становится `verified`. Затем Caddy получает сертификат: в on-demand TLS указан `ask` → `GET /internal/tls/ask?domain=`, который отвечает 200 только для `verified`/`active` доменов. Эндпоинт доступен только из внутренней сети Docker. После выдачи сертификата статус `active`.
4. Активные домены перепроверяются раз в сутки. После 3 неудачных проверок подряд домен получает статус `lost` и перестаёт обслуживаться.
5. Один хост может быть привязан только к одному сайту во всей системе.

## Безопасность

- Сессии хранятся на сервере (Redis). Cookie `httpOnly`, `Secure`, `SameSite=Lax`, **host-only** (без атрибута `Domain`), чтобы поддомены пользователей не получали сессию.
- Мутирующие запросы проверяют заголовок `Origin`. Вход, регистрация, сброс пароля и проверка доменов ограничены rate limit в Redis.
- Пользовательский HTML и JS запрещены. Текст блоков — ограниченный Markdown с санитайзером. Ссылки только `http`, `https`, `mailto`, `tg`.
- Загрузки: проверяем MIME по содержимому, ограничиваем размер, перекодируем картинки (это заодно убирает EXIF). PDF принимаем только для резюме.
- Секреты лежат только в `.env`, который не коммитится. В репозитории есть `.env.example`.

## Рабочий процесс

- Работаем по этапам из раздела ниже. Один этап — одна ветка `stage-N-<кратко>` и один PR. Внутри этапа маленькие коммиты.
- Сообщения коммитов: conventional commits с описанием на русском, например `feat(sites): выбор поддомена`.
- Следующий этап не начинаем без команды пользователя. После этапа даём короткий отчёт: что сделано, как проверить, что отложено.
- Отклонения от этих правил согласовываем с пользователем, потом обновляем этот файл.
